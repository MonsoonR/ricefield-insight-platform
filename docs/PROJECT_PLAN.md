# 稻田智研平台项目计划

> 面向水稻长势与农田环境指标的可视化分析系统

## 1. 项目基本信息

| 项目项 | 内容 |
|---|---|
| 中文名称 | 稻田智研平台 |
| 英文名称 | RiceField Insight Platform |
| 推荐仓库名 | ricefield-insight-platform |
| 项目类型 | 面向研究所研究人员的农田数据可视化与分析平台 |
| 核心用户 | 研究所研究人员、项目维护人员、数据管理员 |
| 第一版目标 | 数据导入、地块地图展示、指标筛选、地块着色、趋势查看、质量报告 |
| 长期目标 | 形成可持续扩展的水稻长势、土壤、环境、光谱、光照数据研究分析平台 |

## 2. 项目定位

稻田智研平台是一个面向研究所研究人员的 Web 分析系统。平台主要服务于水稻试验田、农田地块和环境指标研究，帮助研究人员将定期提供的 Excel、GeoJSON、后续可能的 PDF、遥感、气象、光照等数据统一治理，并通过地图、图表、表格和分析模块进行可视化展示。

项目重点解决三个问题：

1. **数据难整理**：研究人员定期提供多份 Excel 文件，字段、地块编号、时间、单位、格式可能不统一，需要建立统一的数据解析、校验和质量报告机制。
2. **地块难定位**：单看表格很难理解地块空间分布，需要结合卫星地图或地块边界图层，快速定位地块并查看指标状态。
3. **分析难复用**：研究分析需要长期迭代，系统需要从一开始就建立清晰的技术架构、设计规范、接口规范和文档体系。

## 3. 用户与典型场景

### 3.1 研究人员

研究人员主要关注：

- 某个地块当前长势如何；
- 不同地块之间是否存在明显差异；
- 某个指标随时间如何变化；
- 作物长势、叶绿素、氮磷钾、pH、有机质、可溶性总盐分、叶面积指数、株高等指标之间是否存在关系；
- 某些地块是否出现异常；
- 成熟期预测结果是否稳定；
- 数据来源是否可靠；
- 是否可以快速在地图上找到地块。

### 3.2 项目维护人员

维护人员主要关注：

- Excel 如何导入；
- 数据字段如何标准化；
- 地块编号如何匹配；
- 前后端接口如何调用；
- 页面样式如何统一；
- 系统如何部署和备份；
- 后续新增指标、新增页面、新增分析功能如何扩展。

## 4. 最终推荐技术栈

本项目由个人开发者主导，并与 Codex 协作开发。技术栈应优先选择稳定、清晰、易维护、易让 AI 生成规范代码的组合。

## 5. 技术选择结论

### 5.1 前端选择 Vue 3

本项目推荐使用 Vue 3，而不是 React。

主要原因：

- 个人开发者维护成本更低；
- `.vue` 单文件组件结构清晰，模板、逻辑、样式分区明确；
- Codex 生成的 Vue 页面更容易审查和修改；
- 后台系统中表格、筛选、表单、详情页较多，Vue 开发效率高；
- 国内 Vue 资料和排错资源更丰富；
- 与 Ant Design Vue、ECharts、Cesium 的组合足够稳定。

### 5.2 地图选择 CesiumJS

本项目推荐使用 CesiumJS，而不是 MapLibre。

主要原因：

- 开发者已有 Cesium 使用经验；
- 项目需要卫星地图和地块空间展示；
- 后期可能接入遥感影像、NDVI、地形、无人机数据；
- 研究所项目演示效果更强；
- Cesium 可以先轻量使用，后期再扩展三维能力。

第一版中，Cesium 只承担以下功能：

- 加载卫星底图；
- 加载地块 GeoJSON；
- 地块按指标值着色；
- 点击地块显示详情；
- 地块定位；
- 地图与右侧趋势图联动。

第一版暂缓复杂三维能力：

- 三维地形；
- 3D Tiles；
- 倾斜摄影；
- 多时相遥感影像动画；
- 复杂空间分析。

### 5.3 样式方案

MVP 阶段推荐使用：

- Ant Design Vue 组件体系；
- Ant Design Vue 主题 token；
- 页面局部 scoped CSS；
- 设计规范文档统一约束。

MVP 阶段暂缓 Tailwind CSS，减少个人开发者维护成本和样式来源复杂度。

### 6.2 空间数据

- 地块别名；
- 地块所属区域；

### 6.3 后续扩展数据

- 气象数据；
- 光谱数据；

### 6.4 临时样例数据处理原则

开发早期允许使用临时样例数据理解真实文件结构，但临时目录不应成为长期工程依赖。样例数据带来的结论应沉淀为指标字典、数据模型、导入契约、质量检查规则和测试夹具设计。

临时样例目录应保持在 `.gitignore` 中，后续可删除。业务代码、接口、测试和正式文档不应硬编码临时样例目录路径。

## 7. 数据治理原则

### 7.1 统一指标字典

所有指标进入系统前，必须先进入指标字典。

指标字典建议字段：

| 字段 | 含义 |
|---|---|
| metric_code | 指标编码 |
| metric_name | 中文名称 |
| category | 指标类别 |
| unit | 单位 |
| value_type | 数值类型 |
| precision | 小数位数 |
| normal_range | 正常范围 |
| color_scale | 地图色阶 |
| description | 指标说明 |
| source_type | 数据来源类型 |

### 7.2 统一长表结构

Excel 数据解析后统一转换为长表结构。

推荐字段：

| 字段 | 含义 |
|---|---|
| id | 记录 ID |
| plot_id | 地块 ID |
| plot_code | 地块编号 |
| metric_code | 指标编码 |
| value | 指标值 |
| unit | 单位 |
| observed_at | 观测日期 |
| import_batch_id | 导入批次 ID |
| source_file | 来源文件 |
| raw_sheet | 来源工作表 |
| raw_cell | 来源单元格 |
| quality_flag | 数据质量标记 |

### 7.3 地块编号标准化

需要建立地块编号标准化规则，处理：

- 不同写法的同一地块；
- 东区、西区编号差异；
- 重复编号；
- 中文乱码编号；
- Excel 中无法匹配的地块编号；
- GeoJSON 中存在但 Excel 中暂无数据的地块；
- Excel 中存在但 GeoJSON 中无法定位的地块。

### 7.4 数据质量报告

每次导入都必须生成质量报告。

质量报告至少包括：

- 导入批次；
- 文件名称；
- 成功记录数；
- 缺失值数量；
- 异常值数量；
- 未匹配地块；
- 错误单元格；
- 跳过记录；
- 解析耗时；
- 导入状态。

## 11. API 初步规划

第一版建议接口：

| 接口 | 用途 |
|---|---|
| GET /api/health | 健康检查 |
| GET /api/metrics | 获取指标字典 |
| GET /api/plots | 获取地块列表 |
| GET /api/dates | 获取可用观测日期 |
| GET /api/imports | 获取导入批次列表 |
| GET /api/imports/{id}/report | 获取导入质量报告 |
| GET /api/map/layers | 获取地图图层数据 |
| GET /api/plots/{plotId}/summary | 获取地块摘要 |
| GET /api/plots/{plotId}/series | 获取地块趋势 |
| GET /api/analysis/correlation | 获取相关性分析结果 |
| GET /api/analysis/outliers | 获取异常识别结果 |
| GET /api/export/report | 导出分析结果 |

API 设计原则：

- 返回字段命名稳定；
- 错误信息中文可读；
- 业务逻辑写在 service 层；
- 路由函数只处理 HTTP 输入输出；
- 所有接口响应使用 Pydantic schema；
- 前端不要直接依赖 Excel 原始结构。

## 17. 主要风险与应对

| 风险 | 应对方式 |
|---|---|
| Excel 格式变化 | 建立导入模板、解析适配层、质量报告 |
| 地块编号不统一 | 建立地块别名表和标准化规则 |
| 指标单位不统一 | 指标字典中定义单位和转换规则 |
| 数据缺失较多 | 页面和报告中明确标记 |
| 光谱数据和光照数据混淆 | 指标分类中明确区分光谱、气象、光照 |
| Cesium 第一版开发过重 | 只做底图、地块、着色、点击、定位 |
| 页面风格不统一 | 先建立设计规范和基础组件 |
| 个人维护压力大 | 控制 MVP 范围，减少技术栈复杂度 |
| 数据库过早引入拖慢进度 | MVP 先用标准化数据文件，正式版再接 PostGIS |
| Codex 生成代码风格不稳定 | 通过文档、组件规范、目录规范、接口规范约束 |
