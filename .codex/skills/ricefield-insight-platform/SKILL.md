# 稻田智研平台

## 基本原则

Use this skill to keep project work aligned with the current first-stage RiceField Insight Platform baseline. Treat `AGENTS.md` as the source of truth for collaboration rules, technology boundaries, data governance, and commit requirements.

Before changing code, inspect the relevant project docs instead of relying on memory. At minimum read `AGENTS.md`; then read only the docs related to the task:

- Product scope: `docs/PROJECT_PLAN.md`, `docs/ARCHITECTURE.md`
- Backend: `docs/BACKEND_GUIDE.md`, `docs/DATA_MODEL.md`, `docs/API.md`
- Frontend: `docs/FRONTEND_GUIDE.md`, `docs/DESIGN_SYSTEM.md`, `docs/USER_MANUAL.md`
- Metrics/data generation: `docs/METRIC_DICTIONARY.md`, `docs/IMPORT_GUIDE.md`
- Workflow and validation: `docs/CODEX_WORKFLOW.md`, `docs/CHANGELOG.md`

## Scope Guardrails

Keep first-stage work focused on the demoable digital twin loop:

- Simulated scene data generated by the backend
- Program-generated example plot boundaries
- Cesium map display, plot coloring, plot click details, and chart linkage
- Metric filters, plot profiles, metric comparison, warning analysis, and system docs

Do not introduce or restore these without explicit user confirmation: real customer data files, Excel/GeoJSON/PDF/image import flows, import-center pages, import quality reports, Tailwind CSS, complex 3D assets, permissions, automatic reports, multi-project management, or complex spatial analysis.

If the user asks for a path that is longer than needed, explain the simpler path first. If the target changes data model, directory structure, MVP boundary, technology stack, or import contract, propose the change and wait for confirmation before editing.

## Data Rules

Never commit or preserve real Excel, GeoJSON, customer PDFs, customer images, raw client data, or identifiable external data. Tests that need file formats must generate temporary fixtures during the test and clean them up.

All metrics must exist in the metric dictionary before observations use them. Observation data must follow a long-table shape and preserve traceability: plot code, metric code, value, observed time, batch/source information, and quality flag. Every observation batch or generated scene must surface quality status or quality issues; do not hide missing values, outliers, unmatched plots, or parsing errors.

Frontend code must consume normalized APIs. Do not make frontend pages parse raw Excel, GeoJSON, PDF, or image structures.

## Implementation Workflow

1. Check `git status --short` and preserve unrelated user changes.
2. Read the relevant docs listed above.
3. Define the functional target, data fields, API contract, and page structure before editing.
4. For behavior changes, add or update focused tests before implementation when practical.
5. Keep backend route handlers thin: HTTP input/output in routes, business logic in services, schemas in Pydantic models.
6. Keep frontend UI Chinese-first, research/workbench oriented, and consistent with the existing Vue 3 + Ant Design Vue + ECharts + Cesium stack unless the user has explicitly approved a stack change.
7. Update docs whenever data fields, metric codes, import/data generation rules, API responses, page structure, design rules, or deployment behavior change.
8. Always update `docs/CHANGELOG.md` for actual repository changes, with Chinese notes for added/changed/fixed/docs/validation items.
9. Run the relevant validation commands.
10. Commit the completed change after checking the staged scope.

## Validation Commands

Use PowerShell-native commands on Windows. Prefer `pwsh`; if unavailable, Windows PowerShell is acceptable. Do not start by trying `rg` unless it is already confirmed available or the user explicitly requests it.

Select the smallest validation set that proves the change:

```powershell
backend\.venv\Scripts\python.exe -m pytest backend\tests -q
npm --prefix frontend run test:overview
npm --prefix frontend run test:page-linkage
npm --prefix frontend run test:twin-analysis
npm --prefix frontend run test:map
npm --prefix frontend run build
```

For frontend UI/layout changes, also run a browser check or screenshot inspection when a local dev server is available.

## Git Handoff

Before committing:

- Inspect `git status --short`.
- Stage only intended files.
- Exclude virtual environments, caches, generated logs, build outputs, raw data, local databases, and temporary sample files.
- Use a concise Chinese commit message unless the user requests otherwise.

If validation cannot run, state exactly which command was skipped or failed and why.
